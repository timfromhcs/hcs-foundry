# v6 evidence — the 4B class: adapter → fp16 → GGUF

Model: `empero-ai/Qwen3.8-4B-Distill` (Qwen3.5 vision-language checkpoint, 8.68 GiB bf16,
18.0 GiB in fp32, 32 layers: 24 linear-attention + 8 full-attention, vocab 248,320).
Host: 19.8 GiB RAM, free RAM between 3.6 and 7 GiB during these runs (other agent processes).

## 1. Training (done in v4.1, not repeated today)

The last complete 4B training run is the v4.1 one and is unchanged by v6:

```
200 layers quantized · 7,618,560 LoRA parameters
loss 4.453481 → 3.545403 · 2 steps, seq 128
peak RSS 9450.7 MB (4.57 GB of it file-backed) · peak private 6343.5 MB
```

Today's re-run was attempted twice with the same store and aborted both times: the process sat at
271 s CPU without finishing a step while the host held 3.6 GB free and 89 % commit; the numbers
showed page faults, not compute. No new number is invented for it — see
`docs/evidence/v41_int4_4b.md` for the measurement that did complete.

## 2. Adapter → fp16 (new in v6)

```
foundry train merge-int4 --adapter data/training-runs/v41-int4-4b \
  --store data/training-runs/v41-int4-4b/int4-store \
  --out   data/training-runs/v41-int4-4b/merged
```

| Measurement | Result |
|---|---|
| Merged layers | 200 INT4 layers + LoRA |
| Output | 6 shards, **8.70 GiB** fp16 + `model.safetensors.index.json` |
| Duration | **514 s** |
| Peak process memory | ~4.5 GB (one shard buffer plus one layer) |

This is the step that was impossible before v5: the custom `lora_int4.pt` is now a normal
checkpoint that any HF loader can read.

## 3. GGUF export (new in v6)

```
foundry gguf export …/merged --out data/gguf/v6-4b-f16.gguf
```

| Measurement | Result |
|---|---|
| Output | **8264 MiB** F16 |
| Duration | ~8 min (~18–25 MB/s write) |
| Converter | `D:\AI\llama-src\convert_hf_to_gguf.py` |
| Verdict | **works** — the installed converter accepts the Qwen3.5-VL architecture of this checkpoint |

## 4. Quantize

```
foundry gguf quantize data/gguf/v6-4b-f16.gguf --method Q4_K_M --out data/gguf/v6-4b-Q4_K_M.gguf
```

Result: see the release report / manifest line below (filled from the run):

```
llama_quantize: total time = 218741.76 ms
Q4_K_M: 2655 MiB (ratio 0.321)
```

## 5. Run it

```
foundry models run mdl_32e1b442a85fb5982cfe --prompt "Reply with exactly: Hallo Welt" --context 512
```

```json
{
  "text": "Hallo Welt",
  "reasoning": "Thinking Process:\n1.  The user wants a reply with exactly \"Hallo Welt\".\n2.  I need to output only that string, nothing more.",
  "metrics": { "elapsed_seconds": 4.457, "ttft_seconds": 4.333,
               "completion_tokens": 39, "tokens_per_second": 8.75 }
}
```

8.75 tok/s on the Radeon 680M (Vulkan) — slow, but the file is a real GGUF produced from this
machine's own adapter and it answers.

## What this proves

- A 4B checkpoint trained on this machine through the disk-backed INT4 path can be turned into
  a **normal fp16 directory**, a **GGUF** and a **Q4_K_M file that answers**, all by the shipped
  CLI, without ever loading the fp32 model into RAM.
- The Qwen3.5-VL architecture is supported by the installed `convert_hf_to_gguf.py`; the earlier
  "not run" was a missing attempt, not a missing capability.

## Not claimed

- The merged 4B is a two-step fine-tune of 53 records: it is a valid artifact, not a better model.
- 8.75 tok/s is a single measurement at ctx 512 on this iGPU, not a benchmark.
