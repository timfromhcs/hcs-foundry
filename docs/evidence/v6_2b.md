# v6 evidence — the 2B class end to end

Model: `Qwen/Qwen3-1.7B` (public, 3.44 GB + 0.62 GB bf16 shards, 16 layers, hidden 2048,
vocab 151,936 — a dense text model, so the GGUF converter supports it).
Dataset: `ds_e639a804ca5a414d9b12` (53 records, frozen).
Host: Ryzen 7 7735HS, Radeon 680M, 19.8 GiB RAM, ~7 GiB free at start, store on `E:`.

## Chain

| Step | Command | Result |
|---|---|---|
| 1. INT4 store + training | `train int4 --streaming --offload --steps 2 --seq 128 --output data/training-runs/v6-2b` | 196 layers, **loss 5.023045 → 4.080684**, peak RSS **4496 MB**, private peak in the manifest |
| 2. Merge | `train merge-int4 --adapter data/training-runs/v6-2b` | 196 INT4 layers + LoRA → **3 shards, 3.80 GiB fp16**, 179 s |
| 3. GGUF F16 | `gguf export …/merged --out data/gguf/v6-2b-f16.gguf` | **3881 MiB** |
| 4. Quantize | `gguf quantize … --method Q4_K_M` | **1223 MiB, ratio 0.315**, 60.3 s |
| 5. Run | `models run mdl_e756a09d90a8c3a8d5a5 --prompt "Reply with exactly: Hallo Welt"` | `text: "Hallo Welt"` · **51.4 tok/s** · TTFT 5.06 s |

Artifacts:

```
data/training-runs/v6-2b/int4-store/        INT4 store (packed + scales + fp32 leftovers)
data/training-runs/v6-2b/adapter/           lora_int4.pt (custom INT4 adapter)
data/training-runs/v6-2b/merged/            fp16 safetensors, 3 shards + index
data/gguf/v6-2b-f16.gguf                    3881 MiB
data/gguf/v6-2b-Q4_K_M.gguf                 1223 MiB
```

## What this proves

A 2B-class model is trainable on this machine through the disk-backed INT4 path, and the result
is a normal GGUF that `llama-server` loads and answers with. 196 quantized layers is the same
count as the 0.6B run, because the target is the module suffix set, not the parameter count —
the model here is simply wider.

## Not claimed

- Two optimisation steps on 53 records do not make the model better; the loss movement only
  shows that the optimiser ran against the real weights.
- Throughput (51 tok/s at ctx 1024) is a single measurement, not a benchmark.
